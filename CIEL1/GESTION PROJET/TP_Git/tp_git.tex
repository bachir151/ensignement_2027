\section{Pourquoi un gestionnaire de versions ?}

Imaginez votre projet de 2\textsuperscript{e} année (épreuve E6) : trois ou quatre étudiants travaillent
sur les mêmes fichiers (code, documentation, configurations d'équipements). Sans outil adapté,
on voit vite apparaître ceci :

\begin{lstlisting}[style=sortie]
rapport.docx   rapport_v2.docx   rapport_v2_final.docx   rapport_v2_final_OK_bis.docx
\end{lstlisting}

et des questions auxquelles plus personne ne sait répondre : \emph{qui} a modifié ce fichier, \emph{quand}
et \emph{pourquoi} ? Comment revenir à la version qui fonctionnait hier ? Comment réunir le travail de
deux personnes sans écraser celui de l'une d'elles ?

Un \textbf{gestionnaire de versions} (\emph{VCS, Version Control System}) enregistre l'historique complet des
modifications d'un ensemble de fichiers. \textbf{Git} est aujourd'hui le plus utilisé. Il a été créé en 2005 par
Linus Torvalds pour le développement du noyau Linux. Il est \emph{décentralisé} : chaque copie d'un dépôt
contient tout l'historique, et l'on peut travailler sans connexion.

\begin{info}[Git n'est pas GitHub]
\textbf{Git} est un \emph{logiciel} installé sur votre poste.
\textbf{GitHub}, \textbf{GitLab} ou \textbf{Gitea} sont des \emph{services d'hébergement} de dépôts Git
(sites web) qui ajoutent la gestion des collaborateurs, des tickets, etc. On peut utiliser Git sans jamais
utiliser GitHub.
\end{info}

\needspace{8\baselineskip}
\textbf{Vocabulaire essentiel}

\begin{tabularx}{\linewidth}{@{}>{\bfseries\raggedright\arraybackslash}p{4.1cm} X@{}}
\toprule
Dépôt (\emph{repository}) & Dossier suivi par Git. L'historique est stocké dans le sous-dossier caché \cmd{.git}. \\
Commit & Instantané enregistré de l'état des fichiers, avec un auteur, une date, un message et un identifiant unique. \\
Index (\emph{staging area}) & Zone de préparation : ce que l'on a choisi de mettre dans le prochain commit. \\
Branche & Ligne de développement indépendante. Techniquement, un simple pointeur vers un commit. \\
HEAD & Indique où l'on se trouve : en général, la branche courante. \\
Dépôt distant (\emph{remote}) & Copie du dépôt hébergée sur un serveur, habituellement nommée \cmd{origin}. \\
\bottomrule
\end{tabularx}

\section{Installer et configurer Git}

Vérifiez d'abord que Git est installé :
\begin{lstlisting}
git --version
\end{lstlisting}
S'il ne l'est pas : sous Windows, installez \emph{Git for Windows} (\url{https://git-scm.com}) puis
utilisez le terminal \textbf{Git Bash}. Sous Debian ou Ubuntu : \cmd{sudo apt install git}.

Avant le premier commit, Git doit savoir \emph{qui vous êtes}. Remplacez les valeurs entre guillemets :
\begin{lstlisting}
git config --global user.name "Prénom Nom"
git config --global user.email "prenom.nom@exemple.fr"
git config --global init.defaultBranch main
git config --global core.editor nano
git config --global pull.rebase false
\end{lstlisting}

\begin{itemize}
  \item \cmd{user.name} et \cmd{user.email} : identité inscrite dans \emph{chaque} commit. Utilisez la même
  adresse que sur votre compte GitHub ou GitLab.
  \item \cmd{init.defaultBranch main} : nom de la branche principale des nouveaux dépôts
  (anciennement \cmd{master}).
  \item \cmd{core.editor nano} : éditeur que Git ouvre quand il a besoin d'un texte. Pour enregistrer et quitter
  \cmd{nano} : \textbf{Ctrl+O}, \textbf{Entrée}, puis \textbf{Ctrl+X}.
  \item \cmd{pull.rebase false} : demande à \cmd{git pull} de fusionner (\emph{merge}), le comportement le plus
  simple à comprendre (voir partie 9).
  \item \cmd{--global} : le réglage vaut pour tous vos dépôts. Il est stocké dans le fichier \cmd{~/.gitconfig}.
\end{itemize}

\begin{info}[Obtenir de l'aide]
\cmd{git <commande> -h} affiche un résumé des options, \cmd{git help <commande>} la documentation complète.
\end{info}

\begin{exercice}{Configurer Git}
\begin{enumerate}
  \item Affichez la version de Git installée et notez-la. \reponse{1}
  \item Appliquez la configuration ci-dessus avec \emph{vos} informations.
  \item Affichez la configuration avec \cmd{git config --global --list}, puis le contenu du fichier avec
  \cmd{cat ~/.gitconfig}. Que constatez-vous ? \reponse{2}
  \item Quelle commande affiche uniquement l'adresse e-mail configurée ? \reponse{1}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item[1.] Il faut au moins Git 2.23 pour \cmd{git switch} et \cmd{git restore}, et 2.28 pour
  \cmd{init.defaultBranch}. Sinon, mettre Git à jour.
  \item[3.] On retrouve les mêmes informations, rangées en sections \cmd{[user]}, \cmd{[init]}, \cmd{[core]} et
  \cmd{[pull]}. \cmd{git config --global} ne fait qu'écrire dans ce simple fichier texte.
  \item[4.] \cmd{git config user.email}
\end{enumerate}
\end{correction}
\end{exercice}

\section{Les trois zones de Git}

Git n'enregistre rien automatiquement : vous choisissez explicitement ce qui entre dans un commit, en deux temps.

\begin{center}
\begin{tikzpicture}[node distance=2.1cm]
  \node[zone=blue!8]                   (wd)   {Répertoire\\de travail};
  \node[zone=orange!12, right=of wd]   (idx)  {Index\\(\emph{staging area})};
  \node[zone=green!12, right=of idx]   (repo) {Dépôt local\\(dossier \texttt{.git})};
  \draw[->, thick] (wd.north east)  to[bend left=30] node[above]{\texttt{git add}}    (idx.north west);
  \draw[->, thick] (idx.north east) to[bend left=30] node[above]{\texttt{git commit}} (repo.north west);
  \draw[->, thick, dashed] (idx.south west)  to[bend left=30] node[below]{\texttt{git restore}}           (wd.south east);
  \draw[->, thick, dashed] (repo.south west) to[bend left=30] node[below]{\texttt{git restore -{}-staged}} (idx.south east);
\end{tikzpicture}
\end{center}

\begin{enumerate}
  \item \textbf{Répertoire de travail} : les fichiers tels que vous les voyez et les modifiez.
  \item \textbf{Index} : \cmd{git add} y dépose les modifications à inclure dans le prochain commit.
  C'est comme préparer un colis avant de l'expédier.
  \item \textbf{Dépôt} : \cmd{git commit} enregistre le contenu de l'index dans l'historique.
\end{enumerate}

Un fichier peut donc être dans l'un des états suivants, que la commande \cmd{git status} indique :

\begin{tabularx}{\linewidth}{@{}>{\bfseries}l X@{}}
\toprule
non suivi (\emph{untracked}) & Git ne connaît pas encore ce fichier. \\
modifié (\emph{modified})    & Le fichier diffère de la dernière version enregistrée, mais la modification n'est pas indexée. \\
indexé (\emph{staged})       & La modification est prête à entrer dans le prochain commit. \\
validé (\emph{committed})    & Le fichier est identique à la dernière version enregistrée. \\
\bottomrule
\end{tabularx}

\begin{info}[Le réflexe à prendre]
Tapez \cmd{git status} avant et après chaque commande. C'est la commande la plus utile de Git :
elle dit où vous en êtes et suggère souvent la commande suivante.
\end{info}

\section{Créer son premier dépôt}

\textbf{Fil rouge du TP} : vous documentez le réseau de la salle de TP B204 (plan d'adressage, inventaire
du matériel, README). Tous les fichiers sont de simples fichiers texte.

\begin{lstlisting}
mkdir ~/tp-git
cd ~/tp-git
git init
ls -a
git status
\end{lstlisting}

\cmd{git init} crée le sous-dossier caché \cmd{.git}, qui contient tout l'historique et la configuration du dépôt.

\begin{attention}
\begin{itemize}[leftmargin=*]
  \item Ne modifiez jamais le contenu de \cmd{.git} à la main. Le supprimer, c'est perdre tout l'historique.
  \item Ne créez pas de dépôt dans un dossier qui est déjà dans un dépôt. En particulier, ne lancez pas
  \cmd{git init} directement dans votre dossier personnel.
\end{itemize}
\end{attention}

\begin{exercice}{Premier commit}
\begin{enumerate}
  \item Exécutez les commandes ci-dessus. Quel message affiche \cmd{git init} ? Que montre \cmd{ls -a} ?
  \reponse{2}
  \item Créez un fichier \cmd{README.md} et observez son état :
\begin{lstlisting}
echo "# Documentation du réseau de la salle B204" > README.md
git status
\end{lstlisting}
  Dans quelle rubrique apparaît \cmd{README.md} ? \reponse{1}
  \item Indexez le fichier puis observez :
\begin{lstlisting}
git add README.md
git status
\end{lstlisting}
  Dans quelle rubrique apparaît-il maintenant ? \reponse{1}
  \item Validez :
\begin{lstlisting}
git commit -m "Ajout du README"
git status
\end{lstlisting}
  Que signifie le message affiché par \cmd{git status} ? \reponse{2}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item \cmd{Initialized empty Git repository in .../tp-git/.git/} (en français : « Dépôt Git vide initialisé
  dans \ldots »). \cmd{ls -a} montre \cmd{.}, \cmd{..} et \cmd{.git}. \cmd{git status} indique qu'il n'y a encore aucun commit.
  \item \emph{Untracked files} (fichiers non suivis).
  \item \emph{Changes to be committed} (modifications qui seront validées), avec \emph{new file: README.md}.
  \item Le commit affiche \cmd{[main (root-commit) a1b2c3d] Ajout du README}. Ensuite, \cmd{git status} affiche
  \emph{nothing to commit, working tree clean} (rien à valider, la copie de travail est propre) :
  le répertoire de travail est identique au dernier commit.
\end{enumerate}
\end{correction}
\end{exercice}

\begin{exercice}{Le cycle modifier, indexer, valider}
\begin{enumerate}
  \item Avec \cmd{nano plan_adressage.txt}, créez le fichier suivant :
\begin{lstlisting}
# Plan d'adressage - salle B204
VLAN 10  ADMIN    192.168.10.0/24  passerelle 192.168.10.254
VLAN 20  ELEVES   192.168.20.0/24  passerelle 192.168.20.254
\end{lstlisting}
  \item Indexez et validez ce fichier avec le message « Ajout du plan d'adressage ». \reponse{2}
  \item Ajoutez une ligne au README (attention : \cmd{>>} ajoute à la fin du fichier, \cmd{>} l'écrase) :
\begin{lstlisting}
echo "Responsable : Prénom Nom" >> README.md
\end{lstlisting}
  \item Lancez \cmd{git status}. Dans quel état est \cmd{README.md} ? \reponse{1}
  \item Enregistrez cette modification dans un nouveau commit, avec un message pertinent. \reponse{2}
  \item Combien de commits contient le dépôt ? Vérifiez avec \cmd{git log --oneline}. \reponse{1}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item[2.] \cmd{git add plan_adressage.txt} puis \cmd{git commit -m "Ajout du plan d'adressage"}.
  \item[4.] Modifié (\emph{modified}), dans la rubrique \emph{Changes not staged for commit}.
  \item[5.] \cmd{git add README.md} puis, par exemple, \cmd{git commit -m "Ajout du responsable dans le README"}.
  \item[6.] Trois commits, affichés du plus récent au plus ancien.
\end{enumerate}
\end{correction}
\end{exercice}

\begin{info}[Indexer plusieurs fichiers]
\cmd{git add .} indexe tout le contenu du dossier courant. C'est pratique, mais on risque d'embarquer un fichier
non désiré (brouillon, capture, mot de passe). Vérifiez toujours avec \cmd{git status} avant de valider.
\end{info}

\section{Explorer l'historique}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{6.2cm} X@{}}
\toprule
\textbf{Commande} & \textbf{Rôle} \\
\midrule
\cmd{git log}                      & historique détaillé (touche \textbf{q} pour quitter) \\
\cmd{git log --oneline}            & une ligne par commit \\
\cmd{git log --oneline --graph --all} & historique avec toutes les branches (utile en partie 8) \\
\cmd{git show <id>}                & détail d'un commit : auteur, date, message, différences \\
\cmd{git diff}                     & différences entre répertoire de travail et index (ce qui n'est pas indexé) \\
\cmd{git diff --staged}            & différences entre index et dernier commit (ce qui va être validé) \\
\bottomrule
\end{tabularx}

\begin{info}[Identifiant d'un commit]
Chaque commit est identifié par une empreinte (\emph{hash}) de 40 caractères hexadécimaux, calculée à partir de son
contenu, par exemple \cmd{3f2a9c1e...}. Les 7 premiers caractères suffisent en général pour le désigner.
\end{info}

\begin{exercice}{Lire les différences}
\begin{enumerate}
  \item Ajoutez cette ligne à la fin de \cmd{plan_adressage.txt} :
\begin{lstlisting}
VLAN 30  SERVEURS 192.168.30.0/24  passerelle 192.168.30.254
\end{lstlisting}
  \item Sans indexer, tapez \cmd{git diff}. Comment Git signale-t-il la ligne ajoutée ? \reponse{1}
  \item Tapez \cmd{git add plan_adressage.txt}, puis de nouveau \cmd{git diff}. Qu'affiche Git ? Pourquoi ? \reponse{2}
  \item Tapez \cmd{git diff --staged}. Qu'observez-vous ? \reponse{1}
  \item Validez avec le message « Ajout du VLAN 30 (serveurs) ». Avec \cmd{git log --oneline}, repérez l'identifiant
  du commit qui a créé le plan d'adressage, puis affichez-le avec \cmd{git show}. Qui en est l'auteur ? \reponse{1}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item[2.] La ligne est précédée d'un \cmd{+} (en vert). Une ligne supprimée serait précédée d'un \cmd{-} (en rouge).
  \item[3.] Rien : \cmd{git diff} compare le répertoire de travail à l'index. Après \cmd{git add}, ils sont identiques.
  \item[4.] La ligne ajoutée réapparaît : \cmd{git diff --staged} compare l'index au dernier commit.
  \item[5.] L'auteur est celui défini par \cmd{user.name} et \cmd{user.email}, d'où l'importance de la configuration.
\end{enumerate}
\end{correction}
\end{exercice}

\section{Écrire de bons messages de commit}

L'historique n'est utile que s'il est lisible. Quelques règles :
\begin{itemize}
  \item une ligne courte (environ 50 caractères au plus) qui résume la modification ;
  \item décrire \emph{ce qui} change et, si c'est utile, \emph{pourquoi} ;
  \item un commit correspond à \emph{une} modification cohérente : ne mélangez pas « ajout du VLAN 30 » et
  « correction d'une faute dans le README » ;
  \item bannir les messages vides de sens : « modif », « test », « ok »\ldots
\end{itemize}
Pour un message long, tapez \cmd{git commit} sans \cmd{-m} : l'éditeur s'ouvre. Écrivez le résumé sur la première
ligne, laissez une ligne vide, puis donnez les détails.

\begin{exercice}{Bon ou mauvais message ?}
Pour chaque message, indiquez s'il est bon (B) ou mauvais (M) et justifiez en quelques mots.

\renewcommand{\arraystretch}{1.6}
\begin{tabularx}{\linewidth}{@{}l p{7.2cm} c X@{}}
\toprule
& \textbf{Message} & \textbf{B/M} & \textbf{Justification} \\
\midrule
1 & « modif » & & \\
2 & « Ajout du VLAN 30 (serveurs) au plan d'adressage » & & \\
3 & « Correction passerelle VLAN 20 : .254 au lieu de .1 » & & \\
4 & « trucs du mardi » & & \\
5 & « Ajout inventaire, correction README, changement plan, suppression tests » & & \\
6 & « Suppression du mot de passe laissé dans config.txt » & & \\
\bottomrule
\end{tabularx}
\renewcommand{\arraystretch}{1}
\begin{correction}
\begin{enumerate}
  \item M : ne dit rien de la modification.
  \item B : précis, on sait ce qui a changé.
  \item B : précis, et le « pourquoi » est explicite.
  \item M : aucune information exploitable.
  \item M : quatre modifications sans rapport. Il fallait faire quatre commits.
  \item B pour le message, mais il signale un problème de sécurité : le mot de passe \emph{reste dans l'historique}
  (visible avec \cmd{git show}). Il doit être considéré comme compromis et changé (voir partie 7).
\end{enumerate}
\end{correction}
\end{exercice}

\section{Annuler et corriger}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}X >{\raggedright\arraybackslash}p{4.2cm} >{\raggedright\arraybackslash}X@{}}

  & \cmd{git restore --staged fichier}

  & \cmd{git revert <id>}
  & Crée un \emph{nouveau} commit qui annule l'effet de l'ancien. L'historique est conservé. \\

\begin{attention}
\cmd{git commit --amend} \emph{réécrit} l'historique. Ne l'utilisez jamais sur un commit déjà envoyé
(\cmd{git push}) vers un dépôt partagé. Vous croiserez aussi \cmd{git reset --hard} dans des tutoriels :
cette commande est puissante mais destructrice, et elle n'est pas utilisée dans ce TP.
\end{attention}

\begin{exercice}{Réparer ses erreurs}
\textbf{a) « J'ai tout écrasé ! »}
\begin{lstlisting}
echo "oups" > plan_adressage.txt
cat plan_adressage.txt
git status
git restore plan_adressage.txt
cat plan_adressage.txt
\end{lstlisting}
Qu'est devenu le fichier ? L'aurait-on récupéré s'il n'avait jamais été indexé ni validé ? \reponse{2}

\textbf{b) Indexation par erreur}
\begin{lstlisting}
echo "idées en vrac" > brouillon.txt
git add brouillon.txt
git status
\end{lstlisting}
Retirez \cmd{brouillon.txt} de l'index sans le supprimer du disque. Quelle commande utilisez-vous ?
Supprimez ensuite le brouillon avec \cmd{rm brouillon.txt}. \reponse{1}

\textbf{c) Faute dans le message}\\
Créez \cmd{inventaire.csv} :
\begin{lstlisting}
nom;type;ip;salle
SW-B204;switch;192.168.10.2;B204
PC-B204-01;poste;192.168.20.11;B204
\end{lstlisting}
Indexez-le et validez-le avec le message \cmd{"Ajout inventiare"} (faute volontaire). Notez l'identifiant du commit,
puis corrigez :
\begin{lstlisting}
git commit --amend -m "Ajout de l'inventaire du matériel"
git log --oneline
\end{lstlisting}
L'identifiant du commit a-t-il changé ? Pourquoi ? \reponse{2}

\textbf{d) Annuler un commit}\\
Dans le plan d'adressage, remplacez la passerelle du VLAN 10 par \cmd{192.168.10.1}, puis validez avec le message
« Changement de la passerelle du VLAN 10 ». C'était une erreur : annulez ce commit.
\begin{lstlisting}
git revert --no-edit HEAD
git log --oneline
cat plan_adressage.txt
\end{lstlisting}
\cmd{HEAD} désigne ici le dernier commit de la branche courante. Combien de commits l'opération a-t-elle ajoutés ?
Pourquoi préférer \cmd{revert} à \cmd{--amend} quand le commit a déjà été partagé ? \reponse{3}

\begin{correction}
\begin{enumerate}[label=\alph*)]
  \item Le fichier retrouve le contenu de l'index, qui est ici celui du dernier commit. S'il n'avait jamais été indexé ni
  validé, Git n'en aurait aucune copie : le contenu serait perdu. Morale : validez souvent.
  \item \cmd{git restore --staged brouillon.txt}. Le fichier redevient « non suivi ».
  \item Oui. \cmd{--amend} ne modifie pas le commit : il le remplace par un nouveau, dont l'empreinte est différente
  (elle dépend du contenu, du message, de la date\ldots). Ceux qui auraient récupéré l'ancien commit auraient un
  historique incohérent avec le vôtre.
  \item Un seul, intitulé \cmd{Revert "Changement de la passerelle du VLAN 10"}, qui s'ajoute au commit erroné.
  La passerelle revient à \cmd{.254}. \cmd{revert} n'efface rien : l'historique partagé reste cohérent pour toute
  l'équipe, et l'on garde la trace de l'erreur et de sa correction.
\end{enumerate}
\end{correction}
\end{exercice}

\section{\texorpdfstring{Ignorer des fichiers : \texttt{.gitignore}}{Ignorer des fichiers : .gitignore}}

Certains fichiers ne doivent pas être versionnés : fichiers temporaires, journaux, captures réseau, fichiers générés
et surtout \textbf{secrets} (mots de passe, clés, jetons). Le fichier \cmd{.gitignore}, placé à la racine du dépôt,
contient un motif par ligne. Git ignore alors les fichiers \emph{non suivis} qui correspondent à ces motifs.

\begin{attention}[Cybersécurité]
Tout ce qui a été validé reste dans l'historique, même si le fichier est supprimé ensuite. Un secret poussé sur un dépôt
distant doit être considéré comme \textbf{compromis}. Des robots parcourent en permanence les dépôts publics à la
recherche de mots de passe et de clés.
\end{attention}

\begin{exercice}{Mettre en place un .gitignore}
Créez quelques fichiers indésirables :
\begin{lstlisting}
echo "mdp_admin=Azerty123" > secrets.txt
touch capture.pcap debug.log
git status
\end{lstlisting}
Créez ensuite le fichier \cmd{.gitignore} avec \cmd{nano} :
\begin{lstlisting}
# Fichiers sensibles
secrets.txt
# Captures réseau et journaux
*.pcap
*.log
\end{lstlisting}
\begin{enumerate}
  \item Relancez \cmd{git status}. Quels fichiers apparaissent encore ? \reponse{1}
  \item Faut-il versionner le fichier \cmd{.gitignore} lui-même ? Justifiez, puis faites-le. \reponse{2}
  \item Un camarade a validé par erreur \cmd{config_routeur.txt}, qui contient le mot de passe \emph{enable} du routeur,
  puis a ajouté ce fichier au \cmd{.gitignore}. Le problème est-il réglé ? Que faut-il faire ? \reponse{3}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item Seul \cmd{.gitignore} apparaît, comme fichier non suivi.
  \item Oui : il fait partie du projet et doit être partagé avec l'équipe pour que tout le monde ignore les mêmes
  fichiers. \cmd{git add .gitignore} puis \cmd{git commit -m "Ajout du .gitignore"}.
  \item Non. \cmd{.gitignore} n'agit que sur les fichiers \emph{non suivis} : un fichier déjà validé reste suivi, et
  l'ancienne version reste dans l'historique (et sur le dépôt distant s'il a été poussé). Il faut :
  \begin{itemize}
    \item arrêter le suivi sans supprimer le fichier local : \cmd{git rm --cached config_routeur.txt}, puis valider ;
    \item \textbf{surtout}, considérer le mot de passe comme compromis et le changer sur le routeur.
  \end{itemize}
  Purger l'historique est possible (outil \cmd{git filter-repo}), mais c'est délicat et inutile si le dépôt a déjà été
  cloné ou publié.
\end{enumerate}
\end{correction}
\end{exercice}

\section{Travailler avec des branches}

Une \textbf{branche} est une ligne de développement parallèle. On l'utilise pour développer une fonctionnalité ou
tester une idée sans perturber la version stable, conservée sur \cmd{main}. Une fois le travail terminé, on
\textbf{fusionne} (\emph{merge}) la branche dans \cmd{main}.

\begin{center}
\begin{tikzpicture}[x=1.7cm, y=1.2cm]
  \node[commit=green!15] (c1) at (0,0) {C1};
  \node[commit=green!15] (c2) at (1,0) {C2};
  \node[commit=green!15] (c3) at (2,0) {C3};
  \node[commit=blue!15]  (c4) at (3,1) {C4};
  \node[commit=blue!15]  (c5) at (4,1) {C5};
  \node[commit=green!15] (c6) at (3.5,0) {C6};
  \node[commit=green!35, double] (m) at (5,0) {M};
  \draw[thick] (c1) -- (c2) -- (c3) -- (c6) -- (m);
  \draw[thick] (c3) -- (c4) -- (c5) -- (m);
  \node[right=2mm of m, font=\small\ttfamily, text=green!40!black] {main};
  \node[above=1mm of c5, font=\small\ttfamily, text=blue!60!black] {fonctionnalite};
  \draw[->, gray] (0,-0.8) -- node[below, font=\small]{temps} (5,-0.8);
\end{tikzpicture}
\end{center}
{\small Ici, la branche \cmd{fonctionnalite} part de C3. Pendant qu'on y ajoute C4 et C5, \cmd{main} continue avec C6.
Le commit de fusion M réunit les deux lignes.}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{4.8cm} X@{}}
\toprule
\cmd{git branch}          & liste les branches (la branche courante est marquée d'un \cmd{*}) \\
\cmd{git switch -c nom}   & crée la branche \cmd{nom} et bascule dessus \\
\cmd{git switch nom}      & bascule sur une branche existante \\
\cmd{git merge nom}       & fusionne la branche \cmd{nom} \emph{dans la branche courante} \\
\cmd{git branch -d nom}   & supprime une branche déjà fusionnée \\
\bottomrule
\end{tabularx}

\begin{info}[switch ou checkout ?]
Dans beaucoup de tutoriels, vous verrez \cmd{git checkout -b nom}, qui équivaut à \cmd{git switch -c nom}.
\cmd{git switch} (Git $\geq$ 2.23) est plus simple et moins ambigu. Validez ou annulez vos modifications en cours
avant de changer de branche.
\end{info}

\begin{exercice}{Une branche pour le VLAN invités}
\begin{lstlisting}
git switch -c vlan-invites
git branch
\end{lstlisting}
\begin{enumerate}
  \item Quelle branche est marquée d'une étoile ? \reponse{1}
  \item Ajoutez cette ligne au plan d'adressage, puis validez avec le message « Ajout du VLAN 40 (invités) » :
\begin{lstlisting}
VLAN 40  INVITES  192.168.40.0/24  passerelle 192.168.40.254
\end{lstlisting}
  \item Revenez sur \cmd{main} (\cmd{git switch main}) et affichez le plan d'adressage. Où est passé le VLAN 40 ?
  \reponse{2}
  \item Fusionnez : \cmd{git merge vlan-invites}. Quel mot important apparaît dans la sortie ? Que signifie-t-il ?
  \reponse{2}
  \item Visualisez le résultat avec \cmd{git log --oneline --graph --all}, puis supprimez la branche avec
  \cmd{git branch -d vlan-invites}.
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item[1.] \cmd{* vlan-invites}.
  \item[3.] Le VLAN 40 n'existe que dans le commit de la branche \cmd{vlan-invites}. Quand on change de branche, Git
  remet le répertoire de travail dans l'état du dernier commit de la branche choisie. Rien n'est perdu.
  \item[4.] \emph{Fast-forward} (avance rapide) : \cmd{main} n'avait pas évolué depuis la création de la branche. Git a
  simplement avancé le pointeur \cmd{main} jusqu'au commit de \cmd{vlan-invites}, sans créer de commit de fusion.
\end{enumerate}
\end{correction}
\end{exercice}

\begin{exercice}{Provoquer et résoudre un conflit}
\begin{enumerate}
  \item Créez une branche \cmd{passerelle-v2}. Sur cette branche, remplacez la passerelle du VLAN 20 par
  \cmd{192.168.20.1} et validez (« Passerelle VLAN 20 en .1 »).
  \item Revenez sur \cmd{main}. Modifiez \emph{la même ligne} : passerelle \cmd{192.168.20.253}, puis validez
  (« Passerelle VLAN 20 en .253 »).
  \item Affichez \cmd{git log --oneline --graph --all} et dessinez l'allure de l'historique. \reponse{3}
  \item Tentez la fusion avec \cmd{git merge passerelle-v2}. Que répond Git ? Que dit \cmd{git status} ? \reponse{2}
  \item Ouvrez \cmd{plan_adressage.txt}. Git y a inséré des \textbf{marqueurs de conflit} :
\begin{lstlisting}
<<<<<<< HEAD
VLAN 20  ELEVES   192.168.20.0/24  passerelle 192.168.20.253
=======
VLAN 20  ELEVES   192.168.20.0/24  passerelle 192.168.20.1
>>>>>>> passerelle-v2
\end{lstlisting}
  Entre \cmd{<<<<<<< HEAD} et \cmd{=======} se trouve la version de la branche courante (\cmd{main}). Entre
  \cmd{=======} et \cmd{>>>>>>>} se trouve celle de la branche fusionnée.
  \item \textbf{Résolvez le conflit.} La convention de l'établissement place la passerelle sur la dernière adresse
  utilisable du réseau. Éditez le fichier pour ne garder qu'\emph{une} ligne VLAN 20, avec la bonne passerelle, et
  supprimez les trois lignes de marqueurs. Puis :
\begin{lstlisting}
git add plan_adressage.txt
git commit -m "Fusion de passerelle-v2 : passerelle VLAN 20 fixée à .254"
git log --oneline --graph --all
\end{lstlisting}
  \item Pourquoi Git n'a-t-il pas pu fusionner seul ? Dans quel cas y serait-il arrivé ? \reponse{3}
\end{enumerate}
\begin{info}[Faire marche arrière]
Pendant une fusion en conflit, \cmd{git merge --abort} annule la fusion et revient à l'état d'avant.
\end{info}
\begin{correction}
\begin{enumerate}
  \item[3.] Deux lignes qui divergent à partir du commit commun : un commit sur \cmd{passerelle-v2}, un commit sur \cmd{main}.
  \item[4.] \cmd{CONFLICT (content): Merge conflict in plan_adressage.txt} puis
  \cmd{Automatic merge failed; fix conflicts and then commit the result.}
  \cmd{git status} signale \emph{You have unmerged paths} et \emph{both modified:} \cmd{plan_adressage.txt}.
  \item[6.] Aucune des deux versions n'était correcte : la bonne ligne est
  \cmd{VLAN 20  ELEVES   192.168.20.0/24  passerelle 192.168.20.254}. La résolution d'un conflit est une décision
  humaine, ici une décision technique d'administration réseau.
  \item[7.] Les deux branches ont modifié \emph{la même ligne} de façon différente depuis leur ancêtre commun. Git ne
  peut pas savoir quelle version est la bonne. Si les modifications avaient porté sur des parties éloignées du fichier,
  ou sur des fichiers différents, Git aurait fusionné automatiquement.
\end{enumerate}
\end{correction}
\end{exercice}

\section{Collaborer avec un dépôt distant}

Pour travailler à plusieurs, on partage un \textbf{dépôt distant} hébergé sur un serveur (GitHub, GitLab, ou un
serveur Gitea de l'établissement). Chacun travaille dans son dépôt local et se synchronise avec le dépôt distant.

\begin{center}
\begin{tikzpicture}
  \node[zone=green!12] (r) at (0,0)    {Dépôt distant \texttt{origin}\\(GitHub, GitLab\ldots)};
  \node[zone=blue!8]   (a) at (-4.5,-3) {Dépôt local\\étudiant A};
  \node[zone=blue!8]   (b) at (4.5,-3)  {Dépôt local\\étudiant B};
  \draw[->, thick] (a.north) to[bend left=20]  node[left]{\texttt{push}}  (r.west);
  \draw[->, thick] (r.south west) to[bend left=10] node[right, pos=0.6]{\texttt{pull}} (a.north east);
  \draw[->, thick] (b.north) to[bend right=20] node[right]{\texttt{push}} (r.east);
  \draw[->, thick] (r.south east) to[bend right=10] node[left, pos=0.6]{\texttt{clone} / \texttt{pull}} (b.north west);
\end{tikzpicture}
\end{center}

\begin{tabularx}{\linewidth}{@{}>{\raggedright\arraybackslash}p{5.2cm} X@{}}
\toprule
\cmd{git remote add origin <url>} & associe un dépôt distant, nommé \cmd{origin}, au dépôt local \\
\cmd{git remote -v}               & liste les dépôts distants configurés \\
\cmd{git push -u origin main}     & envoie la branche \cmd{main}. L'option \cmd{-u} mémorise le lien : ensuite, \cmd{git push} suffit. \\
\cmd{git pull}                    & récupère les nouveaux commits du distant et les fusionne (\cmd{git fetch} + \cmd{git merge}) \\
\cmd{git clone <url>}             & copie complète d'un dépôt distant, historique compris, avec \cmd{origin} déjà configuré \\
\bottomrule
\end{tabularx}

\begin{info}[Authentification]
Depuis 2021, GitHub refuse le mot de passe du compte pour les opérations Git en HTTPS. Sous Windows,
\emph{Git Credential Manager} (installé avec Git for Windows) ouvre une fenêtre de connexion dans le navigateur.
Sous Linux, utilisez un \emph{jeton d'accès personnel} (\emph{personal access token}) à la place du mot de passe,
ou une clé SSH.
\end{info}

\begin{exercice}{Travailler en binôme (étudiants A et B)}
\begin{enumerate}
  \item \textbf{(A)} Sur GitHub ou GitLab, créez un dépôt \textbf{vide} nommé \cmd{tp-git} : sans README, sans
  \cmd{.gitignore} et sans licence. Sinon, l'historique distant ne correspondrait pas au vôtre.
  \item \textbf{(A)} Reliez votre dépôt local au dépôt distant et envoyez-le (remplacez l'URL par la vôtre) :
\begin{lstlisting}
git remote add origin https://github.com/compte-A/tp-git.git
git push -u origin main
\end{lstlisting}
  Rafraîchissez la page web du dépôt. Que voyez-vous ? \reponse{1}
  \item \textbf{(A)} Ajoutez B comme collaborateur (sur GitHub : \emph{Settings} $\rightarrow$ \emph{Collaborators}).
  \textbf{(B)} Acceptez l'invitation.
  \item \textbf{(B)} Clonez le dépôt de A (dans un dossier qui n'est pas déjà un dépôt Git) :
\begin{lstlisting}
git clone https://github.com/compte-A/tp-git.git tp-git-A
cd tp-git-A
git log --oneline
\end{lstlisting}
  L'historique est-il complet ? \reponse{1}
  \item \textbf{(B)} Ajoutez la ligne \cmd{SW-B204-2;switch;192.168.10.3;B204} à \cmd{inventaire.csv}, validez, puis
  tapez \cmd{git push}.
  \item \textbf{(A)} Tapez \cmd{git pull} et vérifiez le contenu de l'inventaire.
  \item \textbf{Travail simultané.} Sans vous synchroniser, A modifie le titre du README et B ajoute une ligne à
  l'inventaire. Chacun valide. B pousse en premier, puis A tente \cmd{git push}. Que se passe-t-il ?
  Comment A doit-il procéder ? \reponse{3}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item[2.] Les fichiers du projet et l'historique complet des commits.
  \item[4.] Oui : \cmd{git clone} copie tout l'historique, pas seulement la dernière version.
  \item[7.] Le push de A est refusé : \cmd{! [rejected] main -> main (fetch first)}. Le distant contient des commits
  que A n'a pas. A doit faire \cmd{git pull}. Les modifications portant sur des fichiers différents, la fusion est
  automatique. \cmd{nano} s'ouvre alors pour le message du commit de fusion : il suffit d'enregistrer et de quitter.
  En cas de conflit, on le résout comme dans l'exercice 10. A peut ensuite faire \cmd{git push}.
  \\ Prolongement possible : faire modifier à A et B \emph{la même ligne} pour provoquer un conflit à distance.
\end{enumerate}
\end{correction}
\end{exercice}

\begin{info}[La règle d'or du travail en équipe]
\cmd{git pull} avant de commencer à travailler ; des commits petits et fréquents ; \cmd{git push} dès qu'un travail
cohérent est validé.
\end{info}

\section{Défi de synthèse (en autonomie, 30 min)}

Vous rédigez la procédure de sauvegarde de la configuration des switchs de la salle. Essayez de réaliser ce défi
\emph{sans relire les pages précédentes}, en vous aidant uniquement de l'aide-mémoire.

\begin{enumerate}
  \item Créez un nouveau dépôt \cmd{defi-git}, \textbf{en dehors} du dossier \cmd{tp-git}.
  \item Créez \cmd{procedure.md} avec un titre et trois étapes numérotées. Validez.
  \item Ajoutez un \cmd{.gitignore} qui ignore les fichiers \cmd{*.tmp}. Vérifiez-le en créant \cmd{test.tmp}. Validez.
  \item Créez une branche \cmd{ajout-tftp}. Ajoutez une étape « Copier la configuration vers le serveur TFTP
  (\cmd{copy running-config tftp:}) ». Validez, fusionnez dans \cmd{main}, puis supprimez la branche.
  \item Sur \cmd{main}, ajoutez une étape erronée et validez-la. Annulez-la ensuite \emph{sans réécrire l'historique}.
  \item Provoquez puis résolvez un conflit entre \cmd{main} et une branche de votre choix.
  \item \textbf{Rendu} : la sortie de \cmd{git log --oneline --graph --all} et le contenu final de \cmd{procedure.md}.
\end{enumerate}

\begin{correction}
Exemple de solution (les messages peuvent varier) :
\begin{lstlisting}
cd ~ && mkdir defi-git && cd defi-git && git init
nano procedure.md                  # titre + 3 étapes
git add procedure.md && git commit -m "Ajout de la procédure de sauvegarde"
echo "*.tmp" > .gitignore && touch test.tmp && git status   # test.tmp absent
git add .gitignore && git commit -m "Ajout du .gitignore"
git switch -c ajout-tftp
nano procedure.md                  # étape TFTP
git commit -am "Ajout de l'étape de copie TFTP"
git switch main && git merge ajout-tftp && git branch -d ajout-tftp
nano procedure.md                  # étape erronée
git commit -am "Ajout d'une étape erronée"
git revert --no-edit HEAD
# conflit : même ligne modifiée sur une branche et sur main, puis git merge,
# édition du fichier, git add, git commit
git log --oneline --graph --all
\end{lstlisting}
\cmd{git commit -am} indexe et valide en une fois les fichiers \emph{déjà suivis}. On l'accepte si l'élève la découvre,
sans l'exiger. Points de vigilance à l'évaluation : au moins 7 commits, un commit \emph{Revert}, un commit de fusion
issu d'un conflit, aucun marqueur \cmd{<<<<<<<} restant, \cmd{test.tmp} absent de l'historique.
\end{correction}

\section{Testez-vous}

\begin{enumerate}
  \item Quelle commande fait passer une modification du répertoire de travail à l'index ?\\
  $\square$ \cmd{git commit} \quad $\square$ \cmd{git add} \quad $\square$ \cmd{git push} \quad $\square$ \cmd{git init}
  \item Que signifie \emph{nothing to commit, working tree clean} ? \reponse{1}
  \item Quelle est la différence entre \cmd{git revert} et \cmd{git commit --amend} ? \reponse{2}
  \item Que fait \cmd{git pull}, en deux étapes ? \reponse{1}
  \item Vous avez poussé un fichier contenant un mot de passe. Suffit-il de le supprimer et de valider ? \reponse{2}
\end{enumerate}
\begin{correction}
\begin{enumerate}
  \item \cmd{git add}.
  \item Aucune modification en attente : le répertoire de travail et l'index sont identiques au dernier commit.
  \item \cmd{revert} ajoute un nouveau commit qui annule un commit existant, sans réécrire l'historique (utilisable
  après un push). \cmd{--amend} remplace le dernier commit et réécrit l'historique (à réserver aux commits non partagés).
  \item Il récupère les commits du dépôt distant (\cmd{git fetch}) puis les fusionne dans la branche courante (\cmd{git merge}).
  \item Non : le mot de passe reste dans l'historique, localement et sur le dépôt distant. Il faut le considérer comme
  compromis et le changer.
\end{enumerate}
\end{correction}
